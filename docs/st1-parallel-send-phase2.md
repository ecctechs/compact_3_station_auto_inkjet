# ST1 รอบ 2 — ส่งคนละเครื่องพร้อมกัน

ทำต่อใน branch `codex/st1-queue-reliability` วันที่ 26 กันยายน 2026

## ก่อน / หลัง

- เดิม: ได้คิวแล้วส่งทีละเครื่อง เครื่องแรกส่งไม่ผ่านจะหยุดเครื่องถัดไป
- ใหม่: จองตามกฎคิวเดิม เลือกโปรแกรม UV ให้ครบ แล้วเริ่มส่งเครื่องที่ได้คิวพร้อมกัน
- `11`: UV1 + UV2 / `12`, `32`: MK + UV2
- `22`: ส่ง MK แค่รอบแรก รอบสองยังต้องรอปุ่มปล่อยเครื่องตามเดิม
- ถ้าเครื่องใดไม่ว่าง งานของเครื่องนั้นรอคิว ส่วนเครื่องที่ได้คิวส่งได้
- ถ้าเริ่มส่งแล้วเครื่องหนึ่งล้มเหลว อีกเครื่องทำต่อและเก็บผลแยกกัน ไม่ย้อนผลสำเร็จกลับเป็น Waiting
- ผลไม่แน่นอนยังถือคิวไว้ให้ตรวจ ไม่ส่งซ้ำอัตโนมัติ ตามกฎรอบ 1
- แสดงผลรวมหลังทุกเครื่องในชุดจบ ทั้งปุ่มเริ่มงานและการส่งคิวจาก ST3

## จุดที่แก้

- `OrderListUserControl`: เตรียมโปรแกรมก่อนส่ง ใช้ batch ทั้งการเริ่มงานและคิว active; ค้างสถานะกำลังส่งจนทั้งชุดเสร็จ
- `MachineSendBatch`: เริ่มงานคนละเครื่องพร้อมกัน เก็บผล/ข้อผิดพลาดแยกเครื่อง หนึ่งชุดส่งได้เครื่องละหนึ่งรอบ
- `MachineBusy`: กันทางส่งในโปรแกรมเดียวกันใช้เครื่องเดียวกันซ้อนระหว่าง PLC/ส่งคำสั่ง/บันทึกผล
- `OrderDetailUserControl`: ปุ่มส่งตรง MK/UV ในโหมดทดสอบตรวจการถือเครื่องเดียวกันด้วย
- `JobSendService`: ทางส่งคิวไม่เปิดกล่องเลือกโปรแกรมระหว่างส่งแล้ว
- `CpiWriteService`: งาน SQLite ออกจาก UI thread และเรียงการเขียนเมื่อชี้ไฟล์เดียวกัน
- ไม่มีการเปลี่ยน schema, Designer, event wiring, คำสั่งอุปกรณ์ หรือลำดับคำสั่งภายในเครื่อง

## ผลตรวจอัตโนมัติ

- `dotnet build CompactInkjet.sln`: ผ่าน; warning MSB4078 สำหรับ installer `.vdproj` ที่ dotnet build ไม่รองรับ
- ทดสอบ Backend 18 รายการผ่าน บน PostgreSQL ฐานแยก `queue_reliability_test` และ HTTP API ชั่วคราวบน loopback
- ในชุดนี้เรียก C# ApiClient จริง และทดสอบ batch ด้วยตัวส่งจำลองที่รอจุดนัดหมาย: ทั้งสองเครื่องต้องเริ่มก่อนให้เครื่องใดจบ
- ครอบคลุม 11/12/32, 22 ไม่ส่งรอบสอง, exception เครื่องหนึ่งไม่ขวางอีกเครื่อง, ล็อกเครื่องเดียวกัน และไม่ปล่อยล็อกก่อนงานย่อยจบ
- เขียน SQLite ไฟล์ชั่วคราวจริงพร้อมกันสองตาราง ตรวจ Lot ทั้งสอง และตรวจเขียนต่อได้หลังเจอ error
- ตรวจผลบันทึกพร้อมกันทั้งสำเร็จ/ไม่ส่ง/ผลไม่แน่นอน และผลสำเร็จไม่หายตามอีกเครื่อง
- ยังไม่ได้วัดเวลาหรือเปิดโปรแกรมทดสอบกับ MK/UV/PLC จริง และยังไม่ได้เปิด Visual Studio Designer

## เทสหน้างานสั้น ๆ

1. อัปเดต Backend และโปรแกรมทุกสถานีจาก branch ชุดเดียวกัน ปิดโปรแกรมรุ่นเก่าก่อนทดสอบ ถ้ายังพบ `Cannot POST .../begin-send` ต้องตรวจ Backend ที่กำลังรัน
2. เครื่องว่าง: ลอง 11, 12, 32 อย่างละ Lot ดูว่าทั้งสองเครื่องเริ่มรับงานโดยไม่ต้องรออีกเครื่องจบ ตรวจ Lot/Qty/โปรแกรมและชิ้นงานจริงให้ตรงกัน
3. เครื่องหนึ่งไม่ว่าง: ตรวจว่าคิวเครื่องนั้นยังอยู่ เครื่องว่างรับงานได้ และไม่ทับ Lot ที่กำลังผลิต
4. กดเริ่มรัว และกดปล่อยเครื่องรัว: ต้องไม่มีคำสั่งส่งซ้ำหรือข้ามคิว
5. ลอง 22: รอบสองต้องไม่ถูกส่งเองหลังรอบแรกเสร็จส่ง ต้องรอปุ่มปล่อยตามการตั้งค่าเดิม
6. ในช่วงทดสอบที่ควบคุมเครื่องได้ ลองขาดการเชื่อมต่อหลังเริ่มส่ง: อีกเครื่องยังเก็บผลสำเร็จได้ ส่วนผลไม่แน่นอนถือคิวและไม่ส่งซ้ำเอง
7. ส่งจาก ST3 และลอง UV สองเครื่องใช้ CPI บนแชร์จริง ตรวจข้อความไม่สลับกัน หน้าจอไม่ค้าง และผลรวมระบุงานถูกต้อง

## ข้อจำกัดที่ยังต้องจัดการก่อน Production

- ระบบรอบ 1 ยังไม่มีหน้ากู้คืนคิวที่ผลไม่แน่นอน ต้องตรวจอุปกรณ์และกำหนดขั้นตอนกู้คืนก่อนเปิดใช้ผลิตจริง ห้ามลบหลักฐานหรือคืน pending เพื่อข้ามการตรวจ
- การส่งพร้อมกันไม่ใช่การรับประกันว่าเครื่องจะเริ่มพ่นในเวลาเดียวกันหรือชิ้นงานพิมพ์ครบ ต้องตรวจสัญญาณและจังหวะหน้างาน
- ล็อก CPI อยู่ภายในโปรแกรมเดียวกัน ต้องตั้ง path ไฟล์เดียวกันให้เหมือนกัน; mapped drive กับ UNC alias อาจถูกมองเป็นคนละไฟล์ การล็อกจากโปรแกรมภายนอก/เครือข่ายต้องทดสอบจริง
- ปุ่มส่งตรงในโหมดทดสอบยังไม่ใช่การจองคิวร่วมข้าม PC; ไม่ใช้เครื่องมือทดสอบสั่งทับงานผลิต
- ไม่ได้เปลี่ยนกฎตรวจการเชื่อมต่อก่อนเริ่มงาน หรือวิธีหยุด/โหลด/เริ่มของอุปกรณ์
