# วิธี B — รับปุ่มและส่งงานแยกตามเครื่อง

Branch `codex/st1-queue-reliability`

## ก่อน / หลัง

- เดิม `_pushHandling` กันทั้งหน้า: MK กำลังปล่อย/ส่งคิว ทำให้ปุ่ม UV2 ถูกปฏิเสธ และ `_sending` ทำให้รอบตรวจคิวหยุดระหว่างส่ง
- ใหม่กันปุ่มซ้ำแยก MK / UV1 / UV2 และจองสิทธิ์ส่งแยกเครื่องตั้งแต่เตรียมข้อมูลจนบันทึกผล
- กดปล่อย MK และ UV2 พร้อมกัน รับได้ทั้งสองคำขอ; แต่ละคำขอส่งต่อเฉพาะเครื่องของตัวเอง
- ระหว่างเครื่องหนึ่งส่งอยู่ Timer ยังตรวจคิวของอีกเครื่องได้ โดยไม่โหลดตารางทั้งหน้าใหม่
- เครื่องใดส่งและบันทึกผลเสร็จ คืนสิทธิ์เฉพาะเครื่องนั้นทันที แม้อีกเครื่องในชุดเดียวกันยังส่งไม่จบ
- ใช้ token ภายในแยกรอบส่ง ป้องกัน finally ของรอบเก่าไปปลดสิทธิ์รอบใหม่
- นับจำนวนงานส่งที่ค้างจริง แทน bool กลาง ผลส่งที่ทับซ้อนรวมแสดงเมื่อรอบที่ค้างจบ

## กฎที่คงเดิม

- ไม่เก็บการกดเครื่องที่ยังส่งอยู่ไว้ปล่อยในอนาคต การกดซ้ำเครื่องเดิมระหว่างดำเนินการไม่สร้างคำขอเพิ่ม
- API ปล่อยเครื่องยังตรวจ `expected_holder_id`, `sent_at` และผลไม่แน่นอนเหมือนเดิม
- งาน B ต้องเป็นคิวถัดไปของแต่ละเครื่อง ไม่ข้ามงานอื่นเพื่อจับคู่ให้เป็น Lot เดียวกัน
- 22 รอบสองยังต้องรอการปล่อยตามกฎเดิม
- ถ้า UV ยังไม่ได้เลือกโปรแกรม จะรอช่วงไม่มีการคุยอุปกรณ์ก่อนเปิดกล่องเลือก ไม่เดาโปรแกรมให้เอง
- ST3 ยังฝากคิวให้ ST1 ตรวจตาม Timer เดิม จึงอาจมีระยะรอรอบตรวจ แต่ไม่ต้องรอ MK ส่งจบ
- ไม่เปลี่ยน schema, protocol, Designer หรือการเริ่มพ่นของเครื่องจริงให้ตรงเวลาเดียวกัน

## ไฟล์ที่เปลี่ยนในรอบนี้

- `InkjetOperator/Views/OrderListUserControl.cs`: ตัวรับปุ่ม, ตัวส่งคิว, สิทธิ์รายเครื่อง, Timer และการรวมผล
- `tests/OrderListRefreshRegression/Program.cs`: ทดสอบหน้า Order List จริงกับ HTTP จำลอง
- `InkjetBackend/test/queue-reliability.test.js`: เพิ่มกรณี A12 → B12 พร้อมกด MK ซ้ำ

## ผลทดสอบ

- `dotnet build CompactInkjet.sln --no-restore` ผ่าน; warning MSB4078 เดิมของ installer `.vdproj`
- Backend บน PostgreSQL ฐานแยกผ่าน 19/19: A ถือ MK/UV2, B รอ, C รอถัดไป → ปล่อยสองเครื่องพร้อมกับคำขอ MK ซ้ำ → B active ทั้งสองเครื่อง, C ยัง pending
- หน้า Order List จริงใน Windows message loop ใช้ HTTP จำลองทั้งหมด: คำขอปล่อย MK และ UV2 เข้าได้พร้อมกัน; กด MK ซ้ำถูกกัน; UV2 จบก่อนก็ไม่ต้องรอ MK
- ทดสอบทางส่งจริงถึงขั้นขอ `begin-send` ทั้ง MK/UV2 พร้อมกัน และปฏิเสธสิทธิ์ในตัวจำลองก่อนถึง Hardware เพื่อยืนยันไม่มีการติดต่ออุปกรณ์จริง
- ทดสอบ batch ที่ UV2 จบก่อน MK แล้วเริ่ม UV2 รอบใหม่: เมื่อ batch เก่าจบต้องไม่ปลดสิทธิ์รอบใหม่
- regression รีเฟรช/ส่งพร้อมกัน/เขียน CPI และ C# API จากรอบก่อนยังผ่าน
- ยังไม่ได้เปิด Visual Studio Designer หรือทดสอบสัญญาณ PLC/เครื่องพิมพ์จริง

## ลองหน้างาน

1. A รหัส 12 ส่งสำเร็จและถือ MK/UV2; ให้ B12 รอทั้งสองเครื่อง และ C รอถัดไป
2. กดปล่อย MK กับ UV2 พร้อมกัน ทั้งคู่ต้องเปลี่ยนไป B โดยไม่แจ้งให้กดใหม่เพียงเพราะอีกเครื่องกำลังทำงาน
3. กด MK ซ้ำระหว่างกำลังส่ง B ต้องไม่ปล่อย B หรือข้ามไป C
4. ให้เครื่องหนึ่งตอบช้ากว่าอีกเครื่อง ตรวจว่าเครื่องที่เสร็จแล้วไม่ถูกล็อกตามอีกเครื่อง
5. ทดสอบทั้งปุ่มจำลองในจอเดียวและปุ่มจริง ST1/ST3 ตรวจ Lot/โปรแกรมในเครื่องและคิวจริง

ยังต้องใช้ Backend รุ่นเดียวกันทุกสถานี และคิวผลไม่แน่นอนยังต้องตรวจอุปกรณ์ก่อนกู้คืนตามข้อจำกัดรอบ 1
