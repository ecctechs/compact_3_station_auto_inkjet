# ST1 — รอบแรก: ป้องกันคิวซ้ำและส่งซ้ำ

Branch: `codex/st1-queue-reliability` จาก `new-meeting`

## สิ่งที่เปลี่ยน

- การจอง/รับ/ปล่อย/แก้/ล้างคิว ใช้ PostgreSQL advisory lock ใน Transaction เดียวกัน รวมกรณีเครื่องว่างที่ไม่มีแถวให้ล็อก
- ปล่อยเครื่องต้องระบุคิวที่คนกดกำลังปล่อย (`expected_holder_id`) คำขอเก่าจะไม่ข้ามไปปล่อยงานใหม่
- ห้ามปล่อยคิวที่ยังไม่ได้ส่ง หรือยังไม่ทราบผลส่ง
- ก่อนแตะเครื่อง บันทึก `QUEUE_DISPATCH` ลง `print_job_commands` เดิม โดย `success=false` และเก็บเลขคิว/token/ผลใน `payload` ไม่เพิ่มตาราง คอลัมน์ หรือ Index
- หนึ่งคิวได้สิทธิ์เริ่มส่งครั้งเดียว เมื่อคำตอบเริ่มส่งหาย จะไม่เดาว่าส่งได้และไม่ลองส่งเครื่องเอง
- ส่งสำเร็จแล้วบันทึกประวัติคำสั่งกับ `sent_at` ของคิวใน Transaction เดียวกัน ลองบันทึกผลด้วย token เดิมซ้ำได้โดยไม่เพิ่มประวัติซ้ำ
- ส่งไม่ถึงเครื่องแน่นอน: กลับเป็นรอคิว ส่วนผลไม่แน่นอนหรือส่งสำเร็จบางส่วน: ถือเครื่องไว้ตรวจ ห้ามส่งซ้ำอัตโนมัติ
- จบ/ยกเลิกงานเปลี่ยนสถานะและล้างคิวพร้อมกัน ถ้ายังไม่รู้ผลส่ง Backend จะปฏิเสธทั้งสองอย่าง
- ทางสำรองจาก ST3 ผ่านคิวและขั้นตอนบันทึกก่อนส่งเช่นกัน
- หน้ารายละเอียดแสดง “กำลังส่ง / รอตรวจสอบผล” เมื่อยังมีบันทึกส่งที่ไม่จบ

ยังส่งทีละเครื่อง ไม่เปลี่ยนคำสั่ง MK/UV/PLC, กฎ Marking, ตัวเลือกถือ MK รอบสอง หรือ Designer

## การทดสอบอัตโนมัติ

ทดสอบกับ PostgreSQL ชุดใหม่บน loopback แยกจากฐานจริง โดยไม่เปิด WinForms หรือส่งคำสั่งไปอุปกรณ์

1. จองงานเดียวกันพร้อมกัน 12 คำขอ ไม่สร้างคิวซ้ำ
2. หลายงานแย่งเครื่องว่าง ได้ผู้ถือเครื่องรายเดียว
3. ปล่อยคิวเดิมพร้อมกัน ไม่ข้ามงานถัดไป
4. ผู้ส่งสองตัวขอสิทธิ์ส่งคิวเดียวกัน ได้เพียงตัวเดียว
5. คำตอบ begin-send หาย / อ่านใหม่จาก process ใหม่ ยังมีหลักฐานกันส่งซ้ำ
6. ส่งผลสำเร็จซ้ำด้วย token เดิม มีประวัติสำเร็จแถวเดียว
7. จำลอง DB ล้มเหลวกลางการบันทึกผล ประวัติและเวลาในคิวย้อนกลับพร้อมกัน แต่หลักฐานเริ่มส่งยังอยู่
8. ผลไม่แน่นอนห้ามปล่อย ล้าง ยกเลิก ลบ หรือย้อนเป็นรอคิว
9. กรณียืนยันว่าไม่ได้ส่ง กลับเป็น pending และไม่เริ่มส่งเอง
10. MK สองรอบ: ถือรอบสอง / ต่อท้ายคิวตามค่าเดิม
11. ยกเลิกพร้อมล้างคิว และห้ามคำขอเก่ามาจองงานที่ยกเลิกแล้ว
12. การล้างคิวที่ยังไม่ส่ง ไม่ลบแถวที่อีกคำขอรับไปแล้ว
13. เปลี่ยนสถานะยกเลิกล้มเหลว ต้องไม่ทำให้คิวหาย
14. ยกเลิกชนกับเริ่มส่ง ต้องมีเพียงทางเดียวสำเร็จ
15. งานสองเครื่องเก็บผลสำเร็จของเครื่องแรกไว้ เมื่ออีกเครื่องยังไม่ได้ส่ง
16. ใช้ ApiClient ของ C# จริงเรียก Backend ทดสอบ รวม serialization, ข้อความสถานะ และกฎ 11/12/32/22
17. เครื่องที่ยังไม่รู้ผลต้องไม่ถูกอีกเครื่องย้อนสถานะทั้ง Job เป็น Waiting

วิธีรันทดสอบ (ต้องเตรียมฐานว่างชื่อ `queue_reliability_test` บนเครื่องทดสอบ):

```powershell
dotnet build tests/QueueClientRegression/QueueClientRegression.csproj
$env:QUEUE_TEST_DATABASE_URL = 'postgres://<test-user>@127.0.0.1:<test-port>/queue_reliability_test'
node --test InkjetBackend/test/queue-reliability.test.js
dotnet build CompactInkjet.sln
```

ชุดทดสอบล้างข้อมูลในฐานทดสอบนี้ระหว่างกรณี ห้ามชี้ไปฐานที่ต้องเก็บข้อมูล

## ขอบเขตและข้อจำกัดก่อนนำขึ้น Production

- ต้องอัปเดต Backend และโปรแกรมทุกสถานีเป็นชุดเดียวกัน ปิดโปรแกรมรุ่นเก่าก่อน ห้ามใช้รุ่นเก่าปน เพราะรุ่นเก่าไม่รู้จักหลักฐาน `QUEUE_DISPATCH`
- การส่งสำเร็จหมายถึงคำสั่งผ่านตามผลที่ Service เดิมรายงาน ไม่ใช่การยืนยันว่าชิ้นงานพิมพ์ครบจริง
- `sending` ที่ยังค้างอาจเป็นกำลังส่งจริง หรือโปรแกรมหยุดกลางทาง จึงไม่ใช้เวลา Timeout เป็นเหตุให้ปล่อยเครื่องเอง
- ถ้าบันทึกผลกลับ Backend ไม่ได้ โปรแกรมลองบันทึกผลซ้ำหนึ่งครั้งโดยไม่ส่งอุปกรณ์ซ้ำ ถ้ายังไม่ได้ คิวจะถูกถือไว้ ต้องตรวจเครื่องกับบันทึกส่งก่อนแก้ไข
- รอบนี้ยังไม่มีหน้าจอให้คนหน้างานบังคับปลดคิวที่ผลไม่แน่นอน ขั้นตอนกู้คืนหลังตรวจเครื่องต้องตกลงและทดสอบก่อนใช้ Production ห้ามแก้แถวเป็น pending หรือลบ `QUEUE_DISPATCH` เพื่อข้ามการตรวจ
- ปุ่มส่งตรงของโหมดทดสอบใน Order Detail / UV Test ไม่ใช่ Flow ผลิต ห้ามใช้ส่งทับระหว่างมีงาน Production; รอบนี้ไม่ได้ปรับเครื่องมือทดสอบให้เป็นระบบจองเครื่องร่วม
- ล็อกนี้ครอบคลุม API คิวและทางจบ/ยกเลิก/ลบที่แก้ในรอบนี้ ไม่ครอบคลุมการแก้ฐานตรงหรือระบบภายนอกที่ไม่ใช้ API ชุดนี้
- ไม่ได้ทดสอบเครื่อง MK/UV/PLC, จอจริง หรือ Visual Studio Designer ในการตรวจอัตโนมัติ
