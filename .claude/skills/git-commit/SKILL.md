# Git Commit (ภาษาไทย)

ทำให้ทุก commit อ่านย้อนหลังแล้วรู้ทันทีว่า **แก้อะไร และทำไม**
โดยไม่ต้องเปิดโค้ดดู และไม่มีไฟล์ที่ไม่ควรติดไปด้วย

เรื่องที่ผู้ใช้ระบุ: $ARGUMENTS

## ขั้นที่ 1 — ดูว่าแก้อะไรจริง

```bash
git branch --show-current
git status --short
git diff --stat
git diff            # อ่านเนื้อหาที่แก้จริง ไม่เดาจากชื่อไฟล์
git log -5 --format="%h %s"
```

เขียนข้อความจาก **สิ่งที่ diff บอก** ไม่ใช่จากสิ่งที่จำได้ว่าคุยกันไว้
ถ้าอยู่บน `main` ให้บอกผู้ใช้ก่อนว่ากำลังจะ commit ลง main

## ขั้นที่ 2 — ตรวจไฟล์ก่อน commit

หยุดถามผู้ใช้ก่อน ถ้าเจออย่างใดอย่างหนึ่ง:

| เจอ | ทำไมต้องหยุด |
|---|---|
| `.env`, ไฟล์ที่มี password / token / connection string | repo เป็น public ทุกคนเห็น |
| `bin/`, `obj/`, `dist/`, `node_modules/`, `.vs/` | ไฟล์ build ไม่ควรอยู่ใน git |
| ไฟล์ใหญ่เกิน 5 MB (`.zip`, `.mp4`, `.msi`, รูปขนาดใหญ่) | ทำให้ repo บวม ลบออกจากประวัติยาก |
| ไฟล์ที่ไม่เกี่ยวกับเรื่องที่แก้ หรือโฟลเดอร์ที่ไม่รู้ว่าใครสร้าง | อาจเป็นของคนอื่นหรือของเครื่องมืออื่น |
| `C:\ProgramData\...` หรือไฟล์ตั้งค่าเครื่อง (`Setting.config`) | เป็นค่าของเครื่อง ไม่ใช่โค้ด |
| path หรือชื่อที่ดูผิด เช่น `.Codex/` ที่ไม่มีอยู่จริง | มักเกิดจากการแทนคำอัตโนมัติ |

ใช้ `git add <ไฟล์>` ทีละไฟล์ที่ตั้งใจจะ commit — **ห้าม `git add -A` หรือ `git add .`**

ถ้าแก้โค้ดใน `InkjetOperator/` หรือ `InkjetBackend/` แล้วยังไม่ได้ตรวจในรอบนี้ ให้ถามว่าจะรัน `/safe-verify` ก่อนไหม (ไม่บังคับ)

## ขั้นที่ 3 — แยก commit ถ้าแก้หลายเรื่อง

หนึ่ง commit = หนึ่งเรื่องที่พูดได้ในประโยคเดียว
ถ้า diff มีหลายเรื่องที่ไม่เกี่ยวกัน (เช่น แก้ UI + เปลี่ยนเลขเวอร์ชัน + เพิ่มเอกสาร) ให้เสนอแยก commit
เรื่องเดียวกันที่แตะหลายไฟล์ (เช่น client + backend ของฟีเจอร์เดียว) รวมเป็น commit เดียวได้

## ขั้นที่ 4 — เขียนข้อความ

### บรรทัดแรก (หัวเรื่อง)

- ภาษาไทย ประโยคเดียว **บอกว่าโปรแกรมเปลี่ยนไปยังไง** ในมุมคนใช้งาน
- ขึ้นต้นด้วยชื่อหน้าจอหรือส่วนของระบบ ถ้าช่วยให้หาเจอเร็ว เช่น "หน้า Order List …", "ตัวติดตั้ง …", "ST3 …"
- ไม่เกินประมาณ 70 ตัวอักษร ไม่ต้องมีจุดท้าย
- ชื่อปุ่ม ชื่อหน้า ชื่อเครื่อง เขียนตามที่เห็นบนจอ (Order List, Unlock, MK-058, UV2)

### เนื้อหา (เว้น 1 บรรทัดจากหัวเรื่อง)

- บอก **เดิมเป็นยังไง → ตอนนี้เป็นยังไง → ทำไม**
- แก้หลายจุดในเรื่องเดียว ทำเป็นข้อ ๆ ขึ้นต้นด้วย `- `
- ถ้ามีผลกับหน้างาน (ต้องอัปเดตทุกเครื่อง, ต้องตั้งค่าใหม่, คิวเก่าไม่เดินต่อ) ต้องเขียนไว้
- ถ้าตรวจอะไรไปแล้ว (build, เทส) เขียนสั้น ๆ หนึ่งบรรทัด
- ขึ้นบรรทัดใหม่ที่ประมาณ 72 ตัวอักษร ให้อ่านใน terminal ได้
- เรื่องเล็กที่หัวเรื่องบอกครบแล้ว ไม่ต้องมีเนื้อหา

### ห้ามใช้

| อย่าเขียน | เพราะ | เขียนแบบนี้แทน |
|---|---|---|
| `fix`, `update`, `แก้ bug`, `แก้ไข` | ไม่รู้ว่าแก้อะไร | `ปุ่มเริ่มงานหมุนระหว่างส่ง` |
| `skill`, `capture`, `io`, `backend`, `com` | คำเดียว ย้อนดูไม่รู้เรื่อง | `เพิ่มสคริปต์แคปหน้าต่างโปรแกรมโดยไม่ติดลายน้ำ` |
| `4.1 4.2` | เลขข้ออย่างเดียว ไม่บอกเนื้อหา | `4.1 ค่าในหน้า Setting ไม่หายหลัง build ใหม่` |
| ชื่อไฟล์หรือชื่อเมธอดล้วน ๆ | คนอ่านไม่ใช่ทุกคนรู้จักโค้ด | บอกผลที่เห็นบนจอหรือที่เครื่อง |

ถ้างานมาจากรายการที่มีเลขข้อ (เช่น 4.1, 5.2) ใส่เลขไว้หน้าหัวเรื่องได้ แต่ต้องมีคำอธิบายต่อท้ายเสมอ

### กรณีพิเศษ

- เลขเวอร์ชันหลังออก MSI: `เวอร์ชัน 1.0.29`
- merge: `Merge branch '<ชื่อ>' เข้า main` แล้วเนื้อหาบอกว่ารวมเรื่องอะไรเข้ามา
- ย้อน commit: `ย้อนกลับ: <หัวเรื่องเดิม>` แล้วบอกเหตุผล

### บรรทัดท้าย

ถ้าระบบกำหนดบรรทัด attribution (เช่น `Co-Authored-By:`) ให้ใส่ท้ายสุด เว้น 1 บรรทัดจากเนื้อหา

## ขั้นที่ 5 — ยืนยัน แล้ว commit

- ถ้าผู้ใช้แค่ขอให้ **ร่าง** หรือเรียก `/git-commit` → แสดงรายการไฟล์ + ข้อความที่ร่างไว้ แล้วรอผู้ใช้ตอบ "ok" ก่อน
- ถ้าผู้ใช้สั่ง **"commit"** ตรง ๆ และขอบเขตชัด (ไม่เจออะไรในขั้นที่ 2) → commit ได้เลย แล้วแสดงข้อความที่ใช้
- ใช้ heredoc เพื่อรักษาการขึ้นบรรทัดภาษาไทย:

```bash
git commit -F - <<'EOF'
หัวเรื่อง

เนื้อหา
EOF
```

- **ห้าม** `--amend` commit ที่ push ไปแล้ว, ห้าม `--no-verify`, ห้าม push จนกว่าผู้ใช้สั่ง
- hook ล้ม → แก้สาเหตุแล้วสร้าง commit ใหม่ ไม่ข้าม hook

## ขั้นที่ 6 — รายงาน

สั้น ๆ: เลข commit, branch, หัวเรื่อง, จำนวนไฟล์, ยัง push หรือยัง, ไฟล์ที่ยังค้างไม่ได้ commit (ถ้ามี) พร้อมบอกว่าเป็นอะไร
