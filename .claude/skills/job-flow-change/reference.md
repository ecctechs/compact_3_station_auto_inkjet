# กฎของงานพิมพ์ที่ตกลงกันแล้ว

แต่ละข้อมีที่มาในโค้ดหรือเอกสาร ถ้าโค้ดเปลี่ยนจนข้อไหนไม่จริงแล้ว ให้บอกผู้ใช้และอัปเดตไฟล์นี้
ตรวจล่าสุด 19/10/2026 บน main

## 1. Marking method

ที่มา: `InkjetOperator/Services/MarkingMethodService.cs`

- รหัส 2 หลัก: **หลักที่ 1 = Shim, หลักที่ 2 = Plate**
- ค่าแต่ละหลัก: `0` ไม่ทำ, `1` UV, `2` MK, `3` ทำเหมือน `1`
- UV แยกเครื่องตามด้าน: Plate → **UV1**, Shim → **UV2**
- `Code()` แปลง 3 เป็น 1 ก่อนเทียบทุกกฎ — 30 = 10, 31 / 33 = 11, 32 = 12, 13 = 11 (รหัส 32 มีจริงหลายร้อยงาน)
- `21` (Shim MK + Plate UV) ไม่มีอยู่จริง → `NoCase = true` ทำอะไรไม่ได้
- `22` = เข้า MK **สองรอบ** (พ่นเหล็ก → เอาออกไปติดชิม → กลับมาพ่นชิม) Steps = `["MK", "MK"]`
- ลำดับ Steps: MK ก่อน แล้ว UV1 แล้ว UV2

| รหัส | Steps |
|---|---|
| 11 | UV1, UV2 |
| 12 / 32 | MK, UV2 |
| 22 | MK, MK |
| 10 | UV2 |
| 20 / 02 | MK |
| 01 | UV1 |

กฎสถานี (อยู่ในไฟล์เดียวกัน ห้ามเขียนซ้ำในหน้าจอ):

- `VisibleAt`: ST3 เห็นเฉพาะ 10 / 11 / 12 · ST1 เห็นทุกอย่างยกเว้น 10
- `CanStartAt`: 10 เริ่มที่ ST3 เท่านั้น · ที่เหลือเริ่มที่ ST1 เท่านั้น
- `CanCompleteAt`: 10 / 11 / 12 จบที่ ST3 เท่านั้น (UV2 คือขั้นสุดท้าย) — ใช้กับปุ่มจบงานบนจอ
  ยกเว้นการจบอัตโนมัติจากปุ่มหน้าเครื่อง (ข้อ 3 "จบงานอัตโนมัติ") ที่จบที่สถานีของปุ่มสุดท้าย
- `MissingSteps`: นับ **จำนวนครั้ง** ที่ส่งสำเร็จ ไม่ใช่แค่เคยส่งไหม (22 ต้องได้ MK สองครั้ง)

## 2. สถานี

- โปรแกรมตัวเดียว แยกด้วย `MENU_LEVEL`: 0 Scan Barcode, 1 ST1, 3 ST3, 9 ทดสอบหน้างาน, 99 Dev
- **ST3 ไม่คุยกับเครื่องเอง** กดเริ่มแล้วตั้ง remote-start (`PATCH /job/:id/remote-start`) ST1 เป็นคนส่งจริงผ่าน `ProcessRemoteStartsAsync` ในรอบ poll 5 วินาที (`OrderListUserControl.cs`, `PollNormalMs = 5000`) — ST1 ต้องเปิดอยู่
- ST3 ไม่ต้องตรวจการเชื่อมต่อเครื่องก่อนเริ่ม เพราะไม่ได้เป็นคนส่ง

## 3. คิวเครื่อง

ที่มา: `docs/st1-queue-reliability-phase1.md`, `docs/st1-independent-release-method-b.md`, `docs/st1-parallel-send-phase2.md`, `InkjetBackend/services/queueGuard.js`

- ทุกการแก้คิวใน backend อยู่ใต้ `withQueueLock` (`pg_advisory_xact_lock(72419, 1)`) ล็อกเฉพาะช่วงแก้ DB **ไม่ถือล็อกตอนคุยกับเครื่อง**
- **เครื่องไม่ว่าง = เข้าคิว ไม่ใช่ส่งไม่ผ่าน** ห้ามล้างคิวทิ้ง
- FIFO ต่อเครื่อง: งานถัดไปของแต่ละเครื่องต้องเป็นคิวถัดไปจริง ไม่ข้ามงานอื่นเพื่อจับคู่ lot
- หนึ่งคิวได้สิทธิ์เริ่มส่ง (`begin-send`) ครั้งเดียว ก่อนแตะเครื่องบันทึก `QUEUE_DISPATCH` ลง `print_job_commands` เป็นหลักฐาน
- ผลการส่ง:
  - ส่งไม่ถึงเครื่องแน่นอน → กลับเป็นรอคิว (pending) **และไม่เริ่มส่งเอง**
  - ผลไม่แน่นอน (`sending` / `unknown`) หรือสำเร็จบางส่วน → **ถือเครื่องไว้ตรวจ ห้ามส่งซ้ำอัตโนมัติ**
  - ผลไม่แน่นอน **ห้ามปล่อย ล้าง ยกเลิก ลบ หรือย้อนเป็น pending** (`assertNoUnresolved`)
  - ห้ามแก้แถวเป็น pending หรือลบ `QUEUE_DISPATCH` เพื่อข้ามการตรวจ
- ปล่อยเครื่องต้องส่ง `expected_holder_id` — คำขอเก่าจะไม่ไปปล่อยงานใหม่
- ห้ามปล่อยคิวที่ยังไม่ได้ส่ง หรือยังไม่รู้ผล
- จบ / ยกเลิกงาน: เปลี่ยนสถานะและล้างคิวพร้อมกัน ถ้ายังไม่รู้ผลส่ง backend ปฏิเสธทั้งคู่
- ส่งคนละเครื่องพร้อมกันได้ (`MachineSendBatch.RunAsync`) เครื่องหนึ่งล้ม อีกเครื่องทำต่อ เก็บผลแยก ไม่ย้อนผลสำเร็จกลับ
- เครื่องเดียวกันห้ามส่งซ้อน (`MachineBusy`)

### จบงานอัตโนมัติหลังกดปุ่มหน้าเครื่อง

ที่มา: รายงานหน้างาน 18/10/2026 ข้อ 2.3, `OrderListUserControl.AutoCompleteAfterReleaseAsync`

- กดปุ่มหน้าเครื่อง → ปล่อยเครื่องสำเร็จ → ส่งงานถัดไป / เลื่อนหัวกลับเหมือนเดิม → แล้วตรวจงานที่เพิ่งปล่อย
- จบเอง (Success ย้ายไป History) เมื่อครบทุกข้อ: สถานะ `Process` · `MissingSteps` ว่าง · ไม่เหลือแถวคิว pending / active ของงานนี้ที่เครื่องไหน
  - 12: กด MK ไม่จบ (UV2 ยังถือหรือรอคิว) · กด UV2 จบ
  - 22: รอบแรกไม่จบ (ได้ MK ครั้งเดียว) · รอบสองจบ
  - 11: กดเครื่องแรกไม่จบ (อีกเครื่องยังถือ) · กดเครื่องที่สองจบ — อาจจบที่ ST1 ถ้า UV1 กดทีหลัง
- ไม่ถามยืนยัน ไม่บันทึก `MANUAL_COMPLETE` · อ่านไม่ได้ / backend ปฏิเสธ = ไม่จบ งานค้างให้กดจบงานที่จอ
- รุ่นย่อย UV ที่ยังไม่พิมพ์ (`UV_VARIANT_REPEAT`) ไม่ขวางการจบอัตโนมัติ — ปุ่มหน้าเครื่องคือปุ่มจบงาน เปลี่ยนรุ่นใช้ปุ่มบนจอ

### กดจบงาน / ยกเลิกงานบนจอ = เดินคิวต่อเหมือนปุ่มหน้าเครื่อง

ที่มา: รายงานหน้างาน 18/10/2026 ข้อ 2.4, `OrderListUserControl.CompleteJobAsync` / `CancelJobAsync` / `AdvanceFreedMachinesAsync`

- จำเครื่องที่งานถือ (แถว active) ก่อนจบ → `PATCH /job/:id/status` Success (ลบคิวของงานตามเดิม)
  → ปล่อยแต่ละเครื่องด้วย `expected_holder_id = null` ให้ backend ยกเครื่องให้คิวถัดไป
  → ST1 ส่งทันที / ST3 รอ ST1 ส่งรอบ poll / ไม่มีคิวเลื่อนหัวกลับ (`ContinueAfterReleaseAsync` ตัวเดียวกับปุ่มหน้าเครื่อง)
- เดิมไม่เดินคิว: เครื่องว่างแต่ไม่มีใครถือ งานที่รอคิวขึ้นเป็น Waiting เฉย ๆ เหมือนคิวหาย (`QueueWaitLabel` นับว่ารอเฉพาะตอนมีงานอื่นถือเครื่อง)
- งานที่ยังรอคิว (ไม่ได้ถือเครื่อง) จบแล้วไม่ปล่อยเครื่องไหน · ปล่อยไม่ผ่าน (มีคนได้เครื่องไปแล้ว) = คิวเดินแล้ว ไม่ทำอะไรต่อ
- ยกเลิกงานทำแบบเดียวกัน (สถานะ Cancel) · ยกเลิก / จบไม่สำเร็จ = ไม่ปล่อยเครื่อง

### โหมด "ส่งไม่ครบ ไม่ส่งเลย" (ตัวเลือก ปิดไว้เป็นค่าเริ่มต้น)

ที่มา: ข้อตกลงกับผู้ใช้ 17/10/2026, `Services/AllOrNothingSend.cs`, `OrderListUserControl.RollbackJobAsync`, `queueGuard.resolveUnresolved`

- เปิด/ปิดที่ Setting → Station Options (โหมด Dev) คีย์ `SEND_ALL_OR_NOTHING` ใน Setting.config — มีผลที่เครื่อง ST1 (ผู้ส่ง)
- เปิดแล้ว กฎข้างบนที่เรื่อง "ผลไม่แน่นอน" เปลี่ยนเป็น:
  - ก่อนส่ง (ทั้งทางกดเริ่มงานและทางคิว รวมงานจาก ST3) ตรวจการเชื่อมต่อทุกเครื่องของงาน ต่อไม่ติดเครื่องเดียว = ไม่ส่งเครื่องไหนเลย
  - ส่งไม่ผ่านหรือไม่ได้คำตอบ บันทึกเป็น `not_sent` (ไม่มี `unknown`) แล้วล้างคิวทั้งงาน ตั้งงานกลับเป็น Waiting เตือนชื่อเครื่อง และฝาก `remote_error` ให้จอ ST3 ถ้าเป็นงาน 10/11/12
  - งานที่ปล่อยเครื่องไปแล้วบางเครื่อง (รอบสองของ 22 ฯลฯ) ไม่ตีทั้งงานกลับ คิวที่ล้มกลับเป็นรอ ให้กดปุ่มหน้าเครื่องส่งใหม่
    — ตัดสินจากสถานะงานตอนโหลดก่อนส่ง (`Process` = เครื่องอื่นได้งานไปแล้วรอบก่อน) เพราะ `/machine-queue/getAll` ไม่คืนแถว done (แก้ 17/10/2026)
  - คิวที่ค้าง `sending` / `unknown` ปลดได้ด้วยธง `resolve_unresolved` (ปุ่มหน้าเครื่อง, ยกเลิก, จบงาน) หรือ `?resolve=true` (ล้างคิว) — backend เก็บร่องรอย `resolved_by: operator` ไม่ลบประวัติ
  - เครื่องไม่ว่าง ยังเข้าคิวรอเหมือนเดิม
- ข้อแลก: เครื่องที่ส่งผ่านก่อนอีกเครื่องล้ม ได้ข้อมูลไปแล้วจริง (ข้อความเตือนบอกชื่อ) — กดเริ่มงานใหม่ส่งทับ
- ปิดโหมด = กฎเดิมทุกข้อ backend ไม่เห็นธง = ทำงานแบบเดิม (เทส `test/all-or-nothing.test.js`)

### ตัวเลือก "รุ่นย่อย UV2 ให้ ST3 เลือก" (ปิดไว้เป็นค่าเริ่มต้น)

ที่มา: ข้อตกลงกับผู้ใช้ 17/10/2026 (เครื่อง UV2 อยู่ที่ ST3), `Services/Uv2PickAtSt3.cs`, `OrderListUserControl.DeferToSt3Async` / `PickUv2AtSt3Async`

- เปิด/ปิดที่ Setting → Station Options (โหมด Dev) คีย์ `UV2_PICK_AT_ST3` — มีผลที่เครื่อง ST1 (คนกดเริ่มงาน) ST3 ไม่ต้องตั้ง
- ปิด = เดิมทุกข้อ: ST1 เลือกรุ่นทุกเครื่องตอนกดเริ่ม
- เปิด: งานที่มี UV2 และมีเครื่องอื่นด้วย (11 / 12) ที่ ST1 — ถ้าโปรแกรม UV2 **มีรุ่นย่อย (ST1 เห็นหลายไฟล์)** ไม่ถาม ไม่จอง ไม่ตรวจ UV2 ตอนกดเริ่ม ส่งเครื่องอื่นตามปกติ
  - ตกลง 19/10/2026: ถามใช้ `default.uvdx` ที่ ST1 เท่านั้น · เลือกรุ่น UV2 ที่ ST3 · UV1 ที่ ST1 — ไม่พบไฟล์ = ST1 ถาม default ตอนกดเริ่ม · ST1 มองไม่เห็นโฟลเดอร์ = ส่งชื่อเดิมให้เครื่องตัดสิน (ไม่ฝาก ST3)
  - งาน 10 (UV2 อย่างเดียว) เริ่มที่ ST3 จึงยังถาม default ที่ ST3
  - แถวงานขึ้น `Pick UV2 (ST3)` (ทุกสถานี) · ST3 มีปุ่ม "เลือกรุ่น UV2" → เลือกจากโฟลเดอร์ของ ST3 → ยืนยัน → จองคิว UV2 พร้อมชื่อไฟล์ + claim (ทางเดียวกับ ST3 เริ่มงาน 10) → ST1 ส่งในรอบ poll
  - UV2 เข้าคิวตอน ST3 เลือก ไม่ใช่ตอนกดเริ่ม (ไม่จองเครื่องรอคน ไม่ขวางงานอื่น)
  - "รอ ST3 เลือก" อ่านจากข้อมูลที่ทุกสถานีเห็น: สถานะ Process + แผนมี UV2 + ยังไม่เคยส่ง UV2 สำเร็จ + ไม่มีแถวคิว UV2 pending/active
  - ปุ่ม "เลือกรุ่น UV2" ขึ้นเมื่อรอ ST3 เลือกเสมอ ไม่ขึ้นกับ `UV_VARIANT_REPEAT` (เดิมอาศัยปุ่มของตัวเลือกนั้น ปิดไว้งานค้างไม่มีปุ่ม — แก้ 19/10/2026)
- ไฟล์เดียว = ส่งจาก ST1 ทันทีเหมือนเดิม

### ตัวเลือก "พิมพ์รุ่นย่อย UV เพิ่มให้งานใบเดิม" (ปิดไว้เป็นค่าเริ่มต้น)

ที่มา: รายงานหน้างาน 18/10/2026 ข้อ 2.1, `Services/UvVariantService.cs`, `OrderListUserControl.SwitchUvVariantAsync`, backend `POST /machine-queue/switch-program`

- เปิด/ปิดที่ Setting → Station Options คีย์ `UV_VARIANT_REPEAT` — มีผลที่สถานีที่ดูแลเครื่อง (UV1 = ST1 · UV2 = ST3 · Dev เห็นทั้งคู่)
- กดเริ่มงาน เลือกรุ่นแรกเหมือนเดิม · พิมพ์เสร็จแล้วกด **"เปลี่ยนรุ่น UV1/UV2" บนจอ** ไม่ใช้ปุ่มหน้าเครื่อง
  - ปุ่มขึ้นเมื่องานถือเครื่องอยู่ ส่งรุ่นเดิมเข้าไปแล้ว ไม่ได้อยู่ระหว่างส่ง / ไม่รู้ผล (`UvVariantService.HeldRow`) และยังมีรุ่นที่ไม่ได้พิมพ์
  - รายการตัดรุ่นที่พิมพ์แล้ว (payload `program` ของ command ที่สำเร็จ) และรุ่นที่อยู่ในเครื่องออก
  - backend ปิดแถวเดิม (done) + สร้างแถวรอบถัดไปของงานเดิมเป็น active ในทรานแซกชันเดียว งานอื่นแทรกไม่ได้ · รอบ = รอบสูงสุดของงาน+เครื่อง (รวม done) + 1
  - ต้องส่ง `expected_holder_id` · แถวเดิมยังไม่ส่ง / ไม่รู้ผล / งานไม่ใช่ Process = ปฏิเสธ ไม่มีอะไรเปลี่ยน
  - ST1 / Dev ส่งแถวใหม่ทันที · ST3 ให้ ST1 ส่งรอบ poll (ทางเดียวกับแถวที่ถึงคิว)
- ไม่ต้องพิมพ์ครบทุกรุ่น ปุ่มจบงานไม่นับรุ่นที่เหลือ · **ปุ่มหน้าเครื่อง = จบงาน** (จบอัตโนมัติ ข้อ 3)
- เดิม (ก่อน 19/10/2026) ปุ่มเลือกรุ่นถัดไปขึ้นหลังกดปุ่มหน้าเครื่อง แล้วจองรอบ 1 ซ้ำ ซึ่ง enqueue ข้ามเพราะรอบ 1 มีแถว done อยู่แล้ว — ทางนั้นเลิกแล้ว

## 5. การส่งเข้าเครื่อง

- **MK**: `TcpManager` + `MkCompactAdapter` จำกัดเวลา 3 วินาทีต่อคำสั่ง หมดเวลาปิด connection และไม่ส่งคำสั่งที่ค้าง · ช่องว่างไม่ส่ง ให้ไปกรอกก่อน
- **UV**: `UvTcpService.LoadAndStartAsync` — Load สำเร็จ = "ส่งข้อมูลแล้ว" ผล Start รายงานแยก (Start ไม่ผ่านแค่เตือน) · Load ไม่ผ่าน = ถือคิวตรวจ ไม่ส่งซ้ำเอง · เลือกโปรแกรม UV ตั้งแต่ตอนกดเริ่มงาน ไม่เดาให้เอง (ยกเว้น UV2 เมื่อเปิดตัวเลือก "รุ่นย่อย UV2 ให้ ST3 เลือก" — คนที่ ST3 เลือกก่อนจองคิว)
- **PLC MK** (Modbus TCP 502, Unit 1): `PlcOrderService` ส่ง 5 ค่าต่องาน — PostAct / Delay ของสองหัว + Conveyor Speed 1 · เขียนทีละ register (FC 6) · address อ่านจาก `plc_register_maps` ตามชื่อแถว ไม่ฝังในโค้ด
  - ความเร็วสายพานคูณ `CONVEYOR_SPEED_SCALE` (ค่าเริ่มต้น 100) ก่อนเขียน — ทั้งเส้นทางเป็นหน่วย 0.01 Hz
    (เดิมตั้ง 120 เพราะคิดว่าปลายทางเต็มช่วงที่ 50 Hz วัดจริงแล้ว 6000 = 60 Hz แก้เมื่อ 18/10/2026)
  - สายพานว่างไม่ส่ง ให้ไปกรอกก่อน · PLC เขียนไม่ผ่านแค่เตือน ไม่ขวางการส่งเข้าเครื่องพิมพ์
  - เครื่องยังไม่ว่าง ไม่ส่งค่า PLC ทันที รอไปพร้อมงาน
- **ปุ่มกดหน้างาน** (MC protocol ไป PLC แคลมป์ 5012): `PushButtonWatcher` อ่าน bit ตามรอบ `PUSHBTN_POLL_MS` · กดรัวต้องไม่ข้ามคิว · กดตอนจอไม่ว่างไม่ลงมือแต่บอกให้กดใหม่ · ปุ่มแยกรายเครื่อง ส่ง MK อยู่ไม่ขวางการปล่อย UV2
- ปุ่มส่งตรงในโหมดทดสอบ (Order Detail / UV Test) **ไม่ใช่ flow ผลิต** ไม่ผ่านระบบจองเครื่อง

## 6. ติดตั้ง

- แก้ทั้ง backend และ client → ต้องอัปเดต Backend แล้ว restart และอัปเดตโปรแกรมทุกสถานีเป็นชุดเดียวกัน ห้ามใช้รุ่นเก่าปน
- คิวที่ค้างจากรุ่นเก่าไม่ถูกเริ่มเอง ห้ามล้างเพื่อทดลองส่งซ้ำ
