# กฎของงานพิมพ์ที่ตกลงกันแล้ว

แต่ละข้อมีที่มาในโค้ดหรือเอกสาร ถ้าโค้ดเปลี่ยนจนข้อไหนไม่จริงแล้ว ให้บอกผู้ใช้และอัปเดตไฟล์นี้
ตรวจล่าสุด 19/10/2026 บน main · แก้ข้อ 3 "ผลการส่ง" / "ข้ามเครื่อง" / "ส่งซ้ำ" 30/10/2026

## 1. Marking method

ที่มา: `InkjetOperator/Services/MarkingMethodService.cs`

- รหัส 2 หลัก: **หลักที่ 1 = Shim, หลักที่ 2 = Plate**
- ค่าแต่ละหลัก: `0` ไม่ทำ, `1` UV, `2` MK, `3` ทำเหมือน `1`
- UV แยกเครื่องตามด้าน: Plate → **UV1**, Shim → **UV2**
- `Code()` แปลง 3 เป็น 1 ก่อนเทียบทุกกฎ — 30 = 10, 31 / 33 = 11, 32 = 12, 13 = 11 (รหัส 32 มีจริงหลายร้อยงาน)
- `21` (Shim MK + Plate UV) ไม่มีอยู่จริง → `NoCase = true` ทำอะไรไม่ได้
- `22` = เข้า MK **สองรอบ** (พ่นเหล็ก → เอาออกไปติดชิม → กลับมาพ่นชิม) Steps = `["MK", "MK"]`
- ลำดับ Steps: MK ก่อน แล้ว UV1 แล้ว UV2

| รหัส | Steps |
|---|---|
| 11 | UV1, UV2 |
| 12 / 32 | MK, UV2 |
| 22 | MK, MK |
| 10 | UV2 |
| 20 / 02 | MK |
| 01 | UV1 |

กฎสถานี (อยู่ในไฟล์เดียวกัน ห้ามเขียนซ้ำในหน้าจอ):

- `VisibleAt`: ST3 เห็นเฉพาะ 10 / 11 / 12 · ST1 เห็นทุกอย่างยกเว้น 10
- `CanStartAt`: 10 เริ่มที่ ST3 เท่านั้น · ที่เหลือเริ่มที่ ST1 เท่านั้น
- `CanCompleteAt`: 10 / 11 / 12 จบที่ ST3 เท่านั้น (UV2 คือขั้นสุดท้าย) — ใช้กับปุ่มจบงานบนจอ
  ยกเว้นการจบอัตโนมัติจากปุ่มหน้าเครื่อง (ข้อ 3 "จบงานอัตโนมัติ") ที่จบที่สถานีของปุ่มสุดท้าย
- `MissingSteps`: นับ **จำนวนครั้ง** ที่ส่งสำเร็จ ไม่ใช่แค่เคยส่งไหม (22 ต้องได้ MK สองครั้ง)
  - คำสั่ง `SKIP_<ขั้น>` (คนยืนยันข้ามเครื่อง ดูข้อ 3 "ข้ามเครื่อง") นับเป็นขั้นนั้นหนึ่งครั้ง · ทุกที่ที่ถามว่าขั้นนี้ยังต้องส่งไหมใช้ `MarkingMethodService.Covers`

## 2. สถานี

- โปรแกรมตัวเดียว แยกด้วย `MENU_LEVEL`: 0 Scan Barcode, 1 ST1, 3 ST3, 9 ทดสอบหน้างาน, 99 Dev
- **ST3 ไม่คุยกับเครื่องเอง** กดเริ่มแล้วตั้ง remote-start (`PATCH /job/:id/remote-start`) ST1 เป็นคนส่งจริงผ่าน `ProcessRemoteStartsAsync` ในรอบ poll 5 วินาที (`OrderListUserControl.cs`, `PollNormalMs = 5000`) — ST1 ต้องเปิดอยู่
- ST3 ไม่ต้องตรวจการเชื่อมต่อเครื่องก่อนเริ่ม เพราะไม่ได้เป็นคนส่ง

## 3. คิวเครื่อง

ที่มา: `docs/st1-queue-reliability-phase1.md`, `docs/st1-independent-release-method-b.md`, `docs/st1-parallel-send-phase2.md`, `InkjetBackend/services/queueGuard.js`

- ทุกการแก้คิวใน backend อยู่ใต้ `withQueueLock` (`pg_advisory_xact_lock(72419, 1)`) ล็อกเฉพาะช่วงแก้ DB **ไม่ถือล็อกตอนคุยกับเครื่อง**
- **เครื่องไม่ว่าง = เข้าคิว ไม่ใช่ส่งไม่ผ่าน** ห้ามล้างคิวทิ้ง
- FIFO ต่อเครื่อง: งานถัดไปของแต่ละเครื่องต้องเป็นคิวถัดไปจริง ไม่ข้ามงานอื่นเพื่อจับคู่ lot
- หนึ่งคิวได้สิทธิ์เริ่มส่ง (`begin-send`) ครั้งเดียว ก่อนแตะเครื่องบันทึก `QUEUE_DISPATCH` ลง `print_job_commands` เป็นหลักฐาน — ยกเว้นส่งซ้ำที่คนกดเอง (ข้อ "ส่งซ้ำ" ข้างล่าง)
- ผลการส่ง (ตกลงใหม่ 30/10/2026 — **ส่งไม่ผ่าน = ไม่ได้ส่ง** ไม่มีการถือคิวไว้ตรวจ):
  - ส่งไม่ผ่านทุกกรณี → โปรแกรมบันทึก `not_sent` (ไม่ส่ง `unknown` แล้ว) แถวกลับเป็นรอคิว (pending) **และไม่เริ่มส่งเอง**
  - ล้มหลังแตะเครื่องไปแล้ว (ไม่ใช่ล้มที่ด่านตรวจ `SafeToRetry`) → สั่งหยุดเครื่องนั้นก่อน (`JobSendService.StopAfterFailedSendAsync` · MK ทุกหัวที่งานใช้ / UV KEY:84) กันข้อมูลครึ่ง ๆ ถูกพิมพ์ · สั่งหยุดไม่ได้ = เตือนให้ไปดูเครื่อง ไม่ล้ม
  - กดเริ่มงานแล้วไม่มีเครื่องไหนส่งผ่าน = ล้างคิวของงาน งานกลับเป็น Waiting (ทางเดิม `ClearMachineQueueAsync(onlyUnsent)`) กดเริ่มใหม่ได้
  - ทางออกของคนหน้างาน: เริ่มงานใหม่ / ยกเลิกแล้วพิมพ์ใหม่ / จบงาน (ส้ม) — **จบ ยกเลิก ปุ่มหน้าเครื่อง ล้างคิว ทำได้เสมอ**
  - ผลที่ยังเป็น `unknown` (โปรแกรมรุ่นก่อน) หรือ `sending` ค้าง (ST1 ปิดกลางคัน) → ทางของคนหน้างานข้างบนปลดเป็น `not_sent` ให้เองพร้อมร่องรอย `resolved_by` (`settleUnresolved` ใน `queueGuard.js`) · **ยกเว้น `sending` ที่ใหม่กว่า 2 นาที** = กำลังส่งอยู่จริง ตอบ 409 "รอสักครู่แล้วกดใหม่" กันงานถัดไปถูกส่งทับกลางการส่ง
  - ยังห้ามเหมือนเดิม (`assertNoUnresolved`): ลบงาน · แก้แถวเป็น pending · ย้อนผลเป็นไม่ได้ส่ง · begin-send ซ้ำ · เปลี่ยนรุ่น UV · ถอยงานเป็น Waiting
  - จบ / ยกเลิกงานที่ส่งไม่ผ่าน → เดินคิวเครื่องนั้นต่อด้วย (`HeldMachinesAsync` นับแถว pending `not_sent` ของงานด้วย) งานที่รอต่อจากมันไม่ค้าง
  - ห้ามแก้แถวเป็น pending หรือลบ `QUEUE_DISPATCH` เพื่อข้ามการตรวจ
- ปล่อยเครื่องต้องส่ง `expected_holder_id` — คำขอเก่าจะไม่ไปปล่อยงานใหม่
- ห้ามปล่อยคิวที่ยังไม่ได้ส่ง หรือยังไม่รู้ผล
- จบ / ยกเลิกงาน: เปลี่ยนสถานะและล้างคิวพร้อมกัน ถ้ายังไม่รู้ผลส่ง backend ปฏิเสธทั้งคู่
- **พิมพ์ใหม่ (งานที่ยกเลิก)** = เริ่มนับใหม่จริง: ลงหมุด `REPRINT` ในประวัติก่อนเปลี่ยนเป็น Waiting · โปรแกรมเห็นเฉพาะคำสั่งหลังหมุดล่าสุด (`JobAttempt` ตัดที่ PrintJob / ResolvedJobResponse) · backend นับ "เคยส่งสำเร็จ" ตอนส่งไม่ผ่านเฉพาะหลังหมุดเหมือนกัน · ประวัติเก่าอยู่ครบในฐานข้อมูล (ตกลง 19/10/2026)
- ส่งคนละเครื่องพร้อมกันได้ (`MachineSendBatch.RunAsync`) เครื่องหนึ่งล้ม อีกเครื่องทำต่อ เก็บผลแยก ไม่ย้อนผลสำเร็จกลับ
- เครื่องเดียวกันห้ามส่งซ้อน (`MachineBusy`)

### ข้ามเครื่องที่ต่อไม่ได้ / ส่งไม่ผ่าน (คนยืนยันเท่านั้น)

ที่มา: รายงานหน้างาน 18/10/2026 ข้อ 2.2 (ตกลง 19/10/2026: ไม่ทำสวิตช์ซ่อมบำรุง ให้บอกเครื่องที่ไม่ผ่านแล้วยืนยันข้าม), backend `POST /machine-queue/skip`, `OrderListUserControl.UnreachableOrSkipAsync` / `SkipStuckMachineAsync`

- **กดเริ่มงาน (ST1):** ต่อไม่ได้บางเครื่อง → กล่องบอกชื่อเครื่อง + สาเหตุ ถาม "ข้ามแล้วเริ่มงาน" · ยืนยัน = บันทึกข้ามก่อนจองคิว แล้วส่งเครื่องที่เหลือ · ต่อไม่ได้ทุกเครื่อง = ไม่ให้ข้าม เริ่มไม่ได้เหมือนเดิม
  - ลำดับ (ตกลง 22/10/2026): ตรวจการเชื่อมต่อ → ข้าม → **เลือกรุ่นย่อย UV** → กล่องยืนยัน (บอกเครื่องที่ข้าม) → บันทึกข้าม → จองคิว · ตรวจทุกเครื่องในแผนรวม UV2 ที่ฝาก ST3 เลือกรุ่น (ข้ามแล้วไม่จองคิวรอเลือก) · ยกเลิกที่กล่องยืนยัน = ยังไม่บันทึกข้าม งานยังเป็น Waiting
  - ปุ่ม "เลือกรุ่น" / "เปลี่ยนรุ่น" ที่ ST1 ต่อเครื่อง UV นั้นก่อนเปิดกล่องเลือก ต่อไม่ได้ = ไม่เปลี่ยนอะไร (`UvUnreachableAsync`) · ST3 ไม่ตรวจ
- **แถวงาน: ไม่มีปุ่ม "ข้าม" แล้ว (ตกลง 30/10/2026)** — ส่งไม่ผ่านเป็น `not_sent` ไม่มีคิวค้างให้ข้าม · โค้ดปุ่มเดิม (`StuckRows` / `SkipStuckMachineAsync`) ยังอยู่แต่ไม่ถูกเรียก · backend `POST /machine-queue/skip` ยังอยู่ (กล่องข้ามตอนกดเริ่มงานใช้)
  - เดิม: แถวคิวที่ส่งไม่ผ่าน (`not_sent`) หรือไม่รู้ผล (`sending` / `unknown`) → ปุ่ม "ข้ามเครื่อง" · กล่องบอกเครื่อง สถานะ สาเหตุ (`dispatch_error` จาก getAll) ให้ไปตรวจก่อนยืนยัน
  - แถว UV2 ที่**ถือเครื่อง**แต่ยังรอ ST3 เลือกรุ่น (`awaiting_pick`) ข้ามได้ด้วย — เครื่องเสียระหว่างรอ · แถวที่ยังรอคิวไม่มีปุ่ม (ไม่ขวางใคร) (ตกลง 19/10/2026, `StuckRows`) · ปุ่มนี้ขึ้นเฉพาะที่ ST3 ไม่ขึ้นที่ ST1 (ตกลง 27/10/2026) และเฉพาะตอนที่งานยังมีเครื่องอื่นค้าง (ขั้นที่ยังไม่ส่ง หรือยังถือ / รอคิวเครื่องอื่น เช่นงาน 11 ที่ UV1 ยังพิมพ์) — UV2 เป็นขั้นสุดท้าย = ข้ามกับจบงานผลเท่ากัน เหลือแค่ปุ่มจบงาน (`OtherMachinesOutstanding`)
- **MK สองหัว = เครื่องเดียว:** ก่อนส่ง MK ทุกทาง (คิว / ST3 / ปุ่มหน้าเครื่อง) ต่อหัวที่งานใช้ทุกหัวก่อน หัวไหนต่อไม่ได้หรือไม่ได้ตั้ง IP = ไม่ส่งทั้งคู่ ไม่แตะ PLC บันทึก `not_sent` (แถวกลับไปรอ ไม่ส่งซ้ำเอง) → ปุ่ม "ข้ามเครื่อง" ข้ามขั้น MK ทั้งขั้น · หัวที่งานไม่ใช้ต่อไม่ได้ไม่ขวาง (ตกลง 19/10/2026, `SendStepAsync`)
  - ต่อติดตอนตรวจแต่หลุดกลางการส่ง ยังเป็นผลไม่แน่นอนเหมือนเดิม (ถือเครื่องไว้ตรวจ)
- **UV ที่ถูกข้าม:** รุ่นย่อยที่ยังไม่ได้พิมพ์ของเครื่องนั้นไม่นับ — ปุ่มจบงานไม่ส้ม ไม่เตือนตอนจบ งานจบเองได้ (`UvVariantService.CountsRemaining`)
- backend: แถวของงาน+เครื่องนั้นเป็น done (ผลไม่รู้ถูกปลดแบบ `resolveUnresolved` มีร่องรอย) · ไม่มีแถว = สร้างแถว done กันจองซ้ำ · บันทึก `SKIP_<เครื่อง>` · แถวที่ข้ามถือเครื่องอยู่ = ยกให้หัวคิว (FIFO เดียวกับ release)
- โปรแกรม: เครื่องว่างแล้วเดินต่อแบบปุ่มหน้าเครื่อง (`ContinueAfterReleaseAsync`) · ทุกขั้นเสร็จหรือถูกข้าม = จบเอง (รวมงานที่ยังเป็น Waiting)
- ระบบไม่ข้ามเอง · เครื่องที่ ST1 กำลังส่งอยู่ (`CanReleaseNow`) ข้ามไม่ได้จนกว่าจะเสร็จ · ผลไม่รู้ปลดได้ทั้งทางนี้และทางของคนหน้างาน (ปุ่มหน้าเครื่อง / ยกเลิก / จบงาน / ล้างคิว — ตกลง 30/10/2026 ดูข้อ "ผลการส่ง")

### ส่งซ้ำเข้าเครื่องที่งานถืออยู่ (ปุ่ม "ส่ง … ใหม่" ในหน้า Order Detail)

ที่มา: หน้างานแจ้ง 22/10/2026 (กดเริ่มงานแล้ว SWAP หัว MK / แก้ข้อมูล ส่งใหม่ไม่ได้), backend `POST /machine-queue/:id/begin-resend`, `Services/MachineResend.cs`, `OrderListUserControl.ResendCoreAsync` / `RunRemoteResendAsync`

- ปุ่มโชว์เฉพาะเครื่องในแผนของ marking method · **กดได้เฉพาะงานที่ถือเครื่องนั้นอยู่และส่งรอบแรกไปแล้ว** (`MachineResend.Check`) — ยังไม่ส่ง / รอคิว ระบบส่งค่าล่าสุดให้เองตามคิว
- ST1 ส่งเองทุกเครื่อง · ST3 มีแค่ UV2 = ฝาก ST1 (`remote_step = RESEND_UV2`) หมดเวลาไม่ถอยสถานะงาน · โหมด Dev ปุ่มชุดเดิมเป็นปุ่มทดสอบ
- กดแล้วส่งเลยในหน้า Order Detail ไม่ปิดหน้า ไม่ถามยืนยัน (เหมือนปุ่มส่งโหมด Dev — ตกลง 22/10/2026) · ตัวส่งจริงคือ `OrderListUserControl.ResendCoreAsync` ไม่เด้งกล่องเอง คืนผลให้หน้า Order Detail แสดง · SWAP / ABC / บันทึก ไม่ถามส่ง · ส่งเฉพาะค่าที่บันทึกแล้ว
- ส่งผ่านทางเดิม (MK สองหัว · PLC · `MachineBusy`) · งานอื่นแซงไม่ได้ ลำดับคิวไม่เปลี่ยน
- ผล: สำเร็จบันทึก `RESEND_<เครื่อง>` **ไม่ใช่ `<เครื่อง>`** (ไม่นับเป็นรอบ 22 / รุ่นย่อย) · ไม่ถึงเครื่อง = ข้อมูลเดิมยังอยู่ ปล่อยได้ปกติ · ล้มกลางทาง (30/10/2026) = สั่งหยุดเครื่อง บันทึก `not_sent` แถวยังถือเครื่อง ปล่อย / จบ / ยกเลิกได้ กดส่งใหม่อีกครั้งได้
- ไม่แตะ `sent_at` / state / สถานะงาน · ST1 ปิดกลางคันระหว่างส่งซ้ำของ ST3 = ถอนคำขออย่างเดียว ไม่คืนงานเป็นรอเริ่ม
- งานใน History (จบ / ยกเลิก): หน้า Order Detail ไม่มีปุ่มบันทึก SWAP ส่ง หรือสั่งแคลมป์ และแก้ค่าในตารางไม่ได้ (ตกลง 22/10/2026)

### จบงานอัตโนมัติหลังกดปุ่มหน้าเครื่อง

ที่มา: รายงานหน้างาน 18/10/2026 ข้อ 2.3, `OrderListUserControl.AutoCompleteAfterReleaseAsync`

- กดปุ่มหน้าเครื่อง → ปล่อยเครื่องสำเร็จ → ส่งงานถัดไป / เลื่อนหัวกลับเหมือนเดิม → แล้วตรวจงานที่เพิ่งปล่อย
- จบเอง (Success ย้ายไป History) เมื่อครบทุกข้อ: สถานะ `Process` · `MissingSteps` ว่าง · ไม่เหลือแถวคิว pending / active ของงานนี้ที่เครื่องไหน
  - 12: กด MK ไม่จบ (UV2 ยังถือหรือรอคิว) · กด UV2 จบ
  - 22: รอบแรกไม่จบ (ได้ MK ครั้งเดียว) · รอบสองจบ
  - 11: กดเครื่องแรกไม่จบ (อีกเครื่องยังถือ) · กดเครื่องที่สองจบ — อาจจบที่ ST1 ถ้า UV1 กดทีหลัง

### ตัวเลือก "รุ่นย่อย UV2 ให้ ST3 เลือก" (ปิดไว้เป็นค่าเริ่มต้น)

ที่มา: ข้อตกลงกับผู้ใช้ 17/10/2026 (เครื่อง UV2 อยู่ที่ ST3), `Services/Uv2PickAtSt3.cs`, `OrderListUserControl.DeferToSt3Async` / `PickUv2AtSt3Async`

- เปิด/ปิดที่ Setting → Station Options (โหมด Dev) คีย์ `UV2_PICK_AT_ST3` — มีผลที่เครื่อง ST1 (คนกดเริ่มงาน) ST3 ไม่ต้องตั้ง

- เปิด: งานที่มี UV2 และมีเครื่องอื่นด้วย (11 / 12) ที่ ST1 — ถ้าโปรแกรม UV2 **มีรุ่นย่อย (ST1 เห็นหลายไฟล์)** ไม่ถามรุ่น (แต่ตรวจการเชื่อมต่อ UV2 — ตกลง 22/10/2026) **แต่จองคิว UV2 ไว้เลยพร้อม `awaiting_pick`** ส่งเครื่องอื่นตามปกติ
  - ตกลง 19/10/2026: ถามใช้ `default.uvdx` ที่ ST1 เท่านั้น · เลือกรุ่น UV2 ที่ ST3 · UV1 ที่ ST1 — ไม่พบไฟล์ = ST1 ถาม default ตอนกดเริ่ม · ST1 มองไม่เห็นโฟลเดอร์ = ส่งชื่อเดิมให้เครื่องตัดสิน (ไม่ฝาก ST3)
  - งาน 10 (UV2 อย่างเดียว) เริ่มที่ ST3 จึงยังถาม default ที่ ST3
  - แถวงานขึ้น `Pick UV2 (ST3)` (ทุกสถานี) · ST3 มีปุ่ม "เลือกรุ่น UV2" → เลือกจากโฟลเดอร์ของ ST3 → ยืนยัน → **ใส่ program_name ลงแถวที่จองไว้** (`awaiting_pick` กลับเป็น false) ลำดับคิวเดิม → ถึงคิวแล้ว ST1 ส่ง (ST1 ส่งทันที / ST3 รอ poll)
  - **UV2 เข้าคิวตอนกดเริ่ม (ลำดับเดียวกับชิ้นงานบนสายพาน)** — เดิมเข้าตอน ST3 เลือก งานที่กดเริ่มทีหลังแซงได้ เครื่องโหลดโปรแกรมผิดชิ้น (เปลี่ยน 19/10/2026)
  - ถึงคิวแล้วยังไม่เลือก = ถือเครื่องรอ · ST1 ไม่ส่ง ไม่ถามรุ่น (poll / กดเริ่มข้ามแถว `awaiting_pick`) · backend `begin-send` ปฏิเสธแถว `awaiting_pick`

### ตัวเลือก "พิมพ์รุ่นย่อย UV เพิ่มให้งานใบเดิม" (ปิดไว้เป็นค่าเริ่มต้น)

ที่มา: รายงานหน้างาน 18/10/2026 ข้อ 2.1, `Services/UvVariantService.cs`, `OrderListUserControl.SwitchUvVariantAsync`, backend `POST /machine-queue/switch-program`

- เปิด/ปิดที่ Setting → Station Options คีย์ `UV_VARIANT_REPEAT` — มีผลที่สถานีที่ดูแลเครื่อง (UV1 = ST1 · UV2 = ST3 · Dev เห็นทั้งคู่)
- กดเริ่มงาน เลือกรุ่นแรกเหมือนเดิม · พิมพ์เสร็จแล้วกด **"เปลี่ยนรุ่น UV1/UV2" บนจอ** ไม่ใช้ปุ่มหน้าเครื่อง
  - ปุ่มขึ้นเมื่องานถือเครื่องอยู่ ส่งรุ่นเดิมเข้าไปแล้ว ไม่ได้อยู่ระหว่างส่ง / ไม่รู้ผล (`UvVariantService.HeldRow`) และยังมีรุ่นที่ไม่ได้พิมพ์
  - รายการตัดรุ่นที่พิมพ์แล้ว (payload `program` ของ command ที่สำเร็จ) และรุ่นที่อยู่ในเครื่องออก
  - backend ปิดแถวเดิม (done) + สร้างแถวรอบถัดไปของงานเดิมเป็น active ในทรานแซกชันเดียว งานอื่นแทรกไม่ได้ · รอบ = รอบสูงสุดของงาน+เครื่อง (รวม done) + 1
  - ต้องส่ง `expected_holder_id` · แถวเดิมยังไม่ส่ง / ไม่รู้ผล / งานไม่ใช่ Process = ปฏิเสธ ไม่มีอะไรเปลี่ยน
  - ST1 / Dev ส่งแถวใหม่ทันที · ST3 ให้ ST1 ส่งรอบ poll (ทางเดียวกับแถวที่ถึงคิว)
- ไม่บังคับพิมพ์ครบทุกรุ่น แต่ยังเหลือรุ่น (ขั้นที่เริ่มพิมพ์แล้ว) = ปุ่มจบงานสีส้ม กดจบต้องเตือนว่าเหลือรุ่นไหน บันทึก MANUAL_COMPLETE · ปุ่มหน้าเครื่องไม่จบเองจนกว่าจะพิมพ์ครบ (ตกลง 19/10/2026)
- เดิม (ก่อน 19/10/2026) ปุ่มเลือกรุ่นถัดไปขึ้นหลังกดปุ่มหน้าเครื่อง แล้วจองรอบ 1 ซ้ำ ซึ่ง enqueue ข้ามเพราะรอบ 1 มีแถว done อยู่แล้ว — ทางนั้นเลิกแล้ว

## 5. การส่งเข้าเครื่อง

- **MK**: `TcpManager` + `MkCompactAdapter` จำกัดเวลา 3 วินาทีต่อคำสั่ง หมดเวลาปิด connection และไม่ส่งคำสั่งที่ค้าง · ช่องว่างไม่ส่ง ให้ไปกรอกก่อน
- **UV**: `UvTcpService.LoadAndStartAsync` — Load สำเร็จ = "ส่งข้อมูลแล้ว" ผล Start รายงานแยก (Start ไม่ผ่านแค่เตือน) · Load ไม่ผ่าน = ถือคิวตรวจ ไม่ส่งซ้ำเอง · เลือกโปรแกรม UV ตั้งแต่ตอนกดเริ่มงาน ไม่เดาให้เอง (ยกเว้น UV2 เมื่อเปิดตัวเลือก "รุ่นย่อย UV2 ให้ ST3 เลือก" — คนที่ ST3 เลือกก่อนจองคิว)
- **PLC MK** (Modbus TCP 502, Unit 1): `PlcOrderService` ส่ง 5 ค่าต่องาน — PostAct / Delay ของสองหัว + Conveyor Speed 1 · เขียนทีละ register (FC 6) · address อ่านจาก `plc_register_maps` ตามชื่อแถว ไม่ฝังในโค้ด
  - ความเร็วสายพานคูณ `CONVEYOR_SPEED_SCALE` (ค่าเริ่มต้น 100) ก่อนเขียน — ทั้งเส้นทางเป็นหน่วย 0.01 Hz
    (เดิมตั้ง 120 เพราะคิดว่าปลายทางเต็มช่วงที่ 50 Hz วัดจริงแล้ว 6000 = 60 Hz แก้เมื่อ 18/10/2026)
  - สายพานว่างไม่ส่ง ให้ไปกรอกก่อน · PLC เขียนไม่ผ่านแค่เตือน ไม่ขวางการส่งเข้าเครื่องพิมพ์
  - เครื่องยังไม่ว่าง ไม่ส่งค่า PLC ทันที รอไปพร้อมงาน
- **ปุ่มกดหน้างาน** (MC protocol ไป PLC แคลมป์ 5012): `PushButtonWatcher` อ่าน bit ตามรอบ `PUSHBTN_POLL_MS` · กดรัวต้องไม่ข้ามคิว · กดตอนจอไม่ว่างไม่ลงมือแต่บอกให้กดใหม่ · ปุ่มแยกรายเครื่อง ส่ง MK อยู่ไม่ขวางการปล่อย UV2
- ปุ่มส่งตรงในโหมดทดสอบ (Order Detail / UV Test) **ไม่ใช่ flow ผลิต** ไม่ผ่านระบบจองเครื่อง
